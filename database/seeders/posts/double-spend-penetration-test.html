I spent a year on an e-wallet for consumers and merchants in Singapore. Customers could send money to each other, pay merchants by scanning a QR code, top up from cards and banks, and withdraw to local bank accounts, across several currencies. Sellers on the company's marketplace were paid through the same wallet.

A penetration test found something every payments engineer dreads: sending two requests at the same moment could apply a balance change twice.

How the race worked

The transfer logic did what most first versions do:

  1. Read the sender's balance.
  2. Check it covers the amount plus fees.
  3. Debit the sender and credit the receiver.

Each step was correct on its own. The problem is the gap between step 1 and step 3. Two requests arriving within a few milliseconds both read the same balance, both pass the check, and both debit. A customer with $100 could send $100 twice.

// Before: check-then-act with a window in between.
$wallet = Wallet::find($senderId);

if ($wallet->balance < $amount + $fee) {
    throw new InsufficientBalance();
}

// ← a second request can pass the same check here

$wallet->decrement('balance', $amount + $fee);
$receiver->increment('balance', $amount);

This is a classic time-of-check to time-of-use (TOCTOU) bug. Load testing rarely finds it, because it needs two requests from the same account at the same instant, which is exactly what an attacker, or a double-tapped button on a slow network, produces.

Make the transfer all-or-nothing

The fix has two parts. Validate everything that can be validated before touching money, then do the money movement inside one database transaction that locks the rows it depends on.

// 1. Reject early: receiver, PIN, amount, fees, commission and rewards.
$this->validateTransfer($request);
$charges = $this->calculateCharges($request); // fees, commission, rewards

// 2. Move money atomically.
DB::transaction(function () use ($request, $charges) {
    $sender = Wallet::whereKey($request->senderWalletId)->lockForUpdate()->first();
    $receiver = Wallet::whereKey($request->receiverWalletId)->lockForUpdate()->first();

    if ($sender->balance < $charges->totalDebit) {
        throw new InsufficientBalance(); // rolls back everything
    }

    $sender->decrement('balance', $charges->totalDebit);
    $receiver->increment('balance', $charges->receiverCredit);

    Transaction::record($sender, $receiver, $charges);
});

With lockForUpdate(), the second request waits until the first commits, then reads the new balance and fails the check. Every failure path, from a bad PIN to insufficient funds, rolls back the whole transaction, so a transfer either completes fully or leaves no trace.

One practical detail: lock rows in a consistent order (for example by wallet ID), or two transfers going in opposite directions can deadlock each other.

Callbacks are the same bug in disguise

Top-ups had the same shape. Payment gateways notify you by callback, and they retry callbacks they think you missed. If the handler credits the wallet every time it's called, a retried callback becomes free money. The fix is the same idea: verify the callback, then record it against the gateway's reference inside the transaction, and treat a reference you've already seen as done.

While we were in there

A finding like this is a good reason to review the neighbours. We also fixed:

  • a privilege escalation where a sub-admin could reach modules outside their permissions;
  • an access-control flaw where withdrawal details could be read by changing an ID in the URL;
  • cross-site scripting on some admin view pages.

And we added PIN checks on every transfer, signed API orders for merchants, masking of sensitive data in responses, and encryption for the biometric-payment API.

What I took away

Every "check, then act" on shared state is a race until proven otherwise. In money code, the proof is a transaction plus a row lock, and a test that fires two requests at once. A penetration test is cheap compared with finding this bug in production.

A checklist for money-moving code

  • Validate first. Receiver, PIN, amount, fees, commission and rewards are all checked before any balance changes.
  • Calculate every charge before moving money, so there is never a half-applied fee to reverse.
  • One transaction per transfer, with the balance check inside it, after the rows are locked.
  • Lock in a consistent order to avoid deadlocks between opposite transfers.
  • Treat gateway callbacks as retries by default. Record the gateway's reference and ignore one you've already processed.
  • Write the concurrent test. Fire two identical requests at once and assert the balance moved exactly once.

Separately, reporting and dashboards were competing with transactions on one database. Moving reads to read-only connections kept heavy reports from slowing down the payments that customers were waiting on.
