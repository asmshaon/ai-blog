The car-rental platform I worked on for five years originally ran its bookings on a .NET engine built by another team. The team decided to rebuild the booking engine in PHP on Laravel. That was the easy decision. The hard part was doing it without stopping a business that took bookings every minute of every day.

This post is about how we avoided a big-bang cutover, and what made that possible.

Why not switch over in one go?

A single switch-over date is tempting. You build the new engine, test it, pick a quiet night and flip. It fails in predictable ways:

  • Old bookings. Customers who booked on the old engine still need to change, cancel and get refunds after the switch.
  • Unfinished features. The new engine rarely covers every endpoint on day one.
  • No way back. If something breaks at scale, rolling back means losing whatever the new engine did in the meantime.

So instead of one switch, we moved one piece at a time and kept the old path working until nothing needed it.

Step 1: bring the history across

The new engine had to be able to manage bookings it didn't create. Historical bookings from the .NET system were imported into the new booking model, with the commission rules that applied when they were made. Commission is how the business earns money on each rental, so getting it wrong on old bookings would have quietly changed revenue reports.

foreach ($legacy->bookingsSince($from)->lazy() as $old) {
    Booking::updateOrCreate(
        ['legacy_reference' => $old->reference],   // safe to re-run
        [
            'supplier_id'     => $this->suppliers->map($old->supplierCode),
            'status'          => $this->statuses->map($old->status),
            'commission_rule' => $this->commission->ruleAt($old->supplierCode, $old->createdAt),
            'total_cents'     => $old->totalCents,
        ],
    );
}

Keying the import on the legacy reference made it idempotent. We could run it, check the results, fix a mapping and run it again as often as needed before relying on it.

Step 2: bridge what isn't ready yet

Some endpoints were ready before others. For the ones that weren't (cancel, single-vehicle search and the terms and conditions, in version 2.0 of the API), the new API routed calls through a bridge to the old engine. Clients talked to one API throughout. Behind it, each endpoint moved over when its native version was ready, and the bridge for it was removed.

Route::prefix('v2')->group(function () {
    Route::post('bookings', [BookingController::class, 'store']);          // native
    Route::get('vehicles/{id}/terms', LegacyEngineBridge::terms(...));     // bridged for now
    Route::post('bookings/{booking}/cancel', LegacyEngineBridge::cancel(...));
});

This is the "strangler" approach: the new system grows around the old one, taking over one route at a time, until the old one has nothing left to do.

Step 3: build the engine to survive partial failure

A booking touches the supplier, the payment gateway, the database, emails and SMS, and any of them can fail halfway. Supplier prices can also change between search and booking. The new engine creates a booking in stages:

  1. Save an incomplete record first, so nothing is ever lost.
  2. Make the supplier booking.
  3. Take the payment.
  4. Mark it confirmed and send the notifications.

If a step fails, the record says exactly how far it got, and staff get an alert for incomplete bookings instead of discovering them later. If the supplier's price rises between search and booking, the customer is protected from the increase. The engine also supports modifications, cancellations with refund rules, rebook-and-cancel for members, and pending payments.

Step 4: switch the old engine off

Once every endpoint was native and every historical booking could be managed in the new system, the bridge had nothing left to route, and the .NET engine was retired. The switch-off was the last step, not the riskiest one.

What made it work

  • An idempotent import, so history could be brought across and checked repeatedly.
  • One API in front of both engines, so clients never had to know which one answered.
  • Staged bookings and alerts, so partial failures were visible instead of silent.
  • Patience. Retiring the old engine last, not first.

Big-bang rewrites fail because they bet everything on one night. Moving one piece at a time is slower on paper and much faster in practice, because you never have to stop and recover.

If you're planning a similar migration

Start by listing every endpoint the old system serves and every kind of record it owns. For each one, decide how it will be handled during the transition: imported, bridged, or rebuilt natively. That list becomes your migration plan and your progress report at the same time. Anything still marked "bridged" is a reason the old system can't be switched off yet.
