A travel retailer I worked with sells cruises and escorted tours from seven tour operators. Every operator publishes its tours, departures and prices on its own schedule, so the site is fed by dozens of background jobs: nightly imports, webhook processing, cache warming, search index rebuilds and weather updates for ports.

When one of those jobs failed, nobody knew. The first sign was usually a customer or a salesperson noticing that a tour's prices looked old. By then the content could have been stale for days.

Two ways a queue fails

Queues fail in two very different ways, and most setups only watch for one of them.

  • Loud failures. A job throws an exception, runs out of retries and lands in the failed-jobs table. This is easy to detect because something happened.
  • Silent failures. The worker process died, the supervisor didn't restart it, a deploy left the queue paused, or a job is stuck waiting on a lock. Nothing throws. Nothing is logged. Work simply stops being done.

The second kind is more dangerous precisely because it produces no events. You can't alert on an event that never happens, unless you alert on its absence.

Loud failures: tell someone immediately

Laravel fires an event for every failed job. We listen for it and email the team with the job's name, its ID and the stack trace, so the person reading the alert can act without logging in to find out what broke.

use Illuminate\Queue\Events\JobFailed;
use Illuminate\Support\Facades\Event;

Event::listen(function (JobFailed $event) {
    Notification::route('mail', config('ops.alerts_to'))
        ->notify(new QueuedJobFailed(
            job: $event->job->resolveName(),
            id: $event->job->uuid(),
            error: $event->exception,
        ));
});

Two small things made this bearable in practice. First, the failed-jobs table is pruned on a schedule so it doesn't grow forever. Second, work is split across seven named queues, so a heavy nightly import can't block the queue that sends customer notifications.

Silent failures: alert on silence

For the silent kind we added a heartbeat. Every successful job records when it finished. A scheduled command checks that timestamp, and if nothing has completed in four hours it raises an alert.

// After every processed job, remember when work last completed.
Queue::after(fn () => Cache::forever('queue:last_completed_at', now()));

// Scheduled every 15 minutes.
Schedule::call(function () {
    $last = Cache::get('queue:last_completed_at');

    if (! $last || $last->lt(now()->subHours(4))) {
        Notification::route('mail', config('ops.alerts_to'))
            ->notify(new QueueHasGoneQuiet($last));
    }
})->everyFifteenMinutes()->name('queue-heartbeat')->withoutOverlapping();

Four hours sounds long, but it was chosen deliberately. This system always has some job finishing within that window. A shorter window would page people during quiet nights for no reason, and an alert that fires for no reason is an alert people learn to ignore.

Make the pipeline itself self-healing

Alerts are the safety net. The better fix is to make sure a failure can't leave the site in a broken state in the first place. Each operator's import runs as one queued job per tour, so one malformed tour can't stop the rest. A counter per operator tracks how many jobs are still running. When the last one finishes, the search index for that operator is rebuilt.

The important detail is that the same rebuild also runs when the last job fails. Otherwise one bad tour at the end of an import would leave the search index pointing at data from the previous night.

public function handle(): void
{
    try {
        $this->importTour();
    } finally {
        // Runs on success and on failure.
        if (Redis::decr("sync:{$this->operator}:pending") <= 0) {
            RebuildSearchIndex::dispatch($this->operator);
        }
    }
}

What changed

Nothing about this is sophisticated. It is two alerts, a heartbeat and a finally block. But it moved the team from hearing about stale content from customers to hearing about it from the system, usually before anyone outside noticed.

The general lesson I took from it: for every background process, ask how you would know if it stopped. If the honest answer is "someone would complain", you need an alert on silence.

A checklist for your own queues

  • Alert on every final failure, with enough context (job name, ID, error) to act without digging.
  • Alert on silence. Pick a window in which healthy work always completes, and alert when nothing has.
  • Separate queues by urgency, so slow batch work can't delay customer-facing messages.
  • Prune failed jobs on a schedule, so the table stays useful instead of becoming noise.
  • Put cleanup in finally when a follow-up step must run whether the job succeeds or fails.
  • Test the alert. Stop a worker in staging and confirm the heartbeat fires. An alert that has never fired is an assumption, not a safeguard.
