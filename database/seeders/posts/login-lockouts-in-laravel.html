Every public login form is eventually found by a script that tries passwords. On two recent projects, a vendor console for an event food-ordering platform and the public site of a travel retailer, I added protection against password guessing. The two needed different tools, and the details mattered more than the headline feature.

What "rate limiting" usually gets wrong

The simplest approach is a throttle on the login route: at most N requests per minute per IP. It helps a little, but it has two problems:

  • It limits requests, not failed attempts. A real user who mistypes twice and a script that tries a thousand passwords look the same until the limit is hit.
  • The window is fixed. A script that waits for the minute to roll over gets a fresh allowance every time.

What we wanted instead was a lockout on failures, keyed by account and address, with a window that restarts if you keep trying.

A sliding lockout on failed attempts

On the vendor console, sign-in is locked for five minutes after the fifth failed attempt. The part people often miss is that trying again while locked restarts the five minutes. A script that keeps hammering never gets back in. A person who waits a few minutes does.

use Illuminate\Support\Facades\RateLimiter;

public function store(LoginRequest $request): RedirectResponse
{
    $key = 'login:'.Str::lower($request->input('email')).'|'.$request->ip();

    if (RateLimiter::tooManyAttempts($key, maxAttempts: 5)) {
        // Trying while locked restarts the window.
        RateLimiter::clear($key);
        RateLimiter::increment($key, decaySeconds: 300, amount: 5);

        throw ValidationException::withMessages([
            'email' => 'Too many attempts. Try again in 5 minutes.',
        ]);
    }

    if (! Auth::attempt($request->only('email', 'password'))) {
        RateLimiter::increment($key, decaySeconds: 300);

        throw ValidationException::withMessages(['email' => __('auth.failed')]);
    }

    RateLimiter::clear($key);
    $request->session()->regenerate();

    return redirect()->intended('/dashboard');
}

Keying on both the email and the IP keeps one attacker from locking every vendor out of their own account, while still stopping a single source from guessing a single password.

The edge cases that actually got exploited

The lockout was the headline. The fixes around it were just as important:

  • Stale cookies. A session cookie from before a password change or account removal could still get through part of the flow. We now block sign-in with a stale cookie, clear stale sessions, and refuse sign-in entirely for deleted users.
  • Role checks per route. Authentication tells you who someone is, not what they may do. Every console route checks the role it needs, instead of relying on "they're logged in".
  • A trail. Admins can see which devices a vendor signs in from, and an activity log records actions with the real client IP. Behind a load balancer, that means reading the forwarded header from a trusted proxy, not the proxy's own address.
  • Unused routes removed. The safest endpoint is the one that no longer exists.

Blocking abusive addresses on a public site

The travel retailer's problem was different: bots hitting both the login and the API. There we block the address itself. Three failed logins within five minutes adds the IP to a block list. Addresses that exceed the API rate limits go on the same list, with a counter. Blocked addresses get a clear "restricted" response instead of a timeout.

Two exceptions keep this from hurting the business:

  • A whitelist for known partners and the office.
  • Known search-engine crawlers stay allowed. Blocking them would quietly remove tour pages from search results, which costs far more than a few bot requests.

A daily summary of blocked addresses goes to the team, so a sudden spike, or a partner accidentally blocked, is noticed within a day.

What I'd tell a team starting from scratch

Count failures, not requests. Make the lockout window slide. Key on the account and the address together. Then spend as much time on sessions, roles and logging as on the lockout itself, because that's where the quieter holes are.

How to check your own login

  • Try six wrong passwords in a row. Does the sixth attempt get a clear message, and does waiting actually let you back in?
  • Keep retrying while locked. Does the lockout extend, or does a fixed window reset in your favour?
  • Sign in, change the password in another browser, then use the old session. Is it still accepted?
  • Delete a test user and try their credentials. Are they refused everywhere, including API routes?
  • Check what IP your logs record behind the load balancer. Is it the visitor's, or the proxy's?

Each of these takes minutes to try, and together they cover the gaps that a lockout alone leaves open.
